What BIOS is

A component system for WordPress plugin administration screens, written to be read and applied by people and by software agents.

  • The system is one stylesheet, tokens.css: 49 components in six groups, and the tokens they consume. It is the owner’s file to edit.
  • Components are BEM class blocks. No JavaScript is required for rendering; interactive behavior is left to the host page (examples/bios.js covers the common cases).
  • Dimensions, colors, and type are taken from measurements of the WordPress administration interface (WP 7.0).
  • Configuration is done through a small set of custom properties (knobs). Component rules are not edited.
  • Two documents carry the rules: docs/contract.md (what the system is: tokens, inventory, the nine hard rules) and docs/agent-heuristics.md (how to choose between components).

Quick start

Open the examples, copy the closest screen, and edit markup first.

  1. Open examples/styleguide.html. Use it as the component index and visual reference.
  2. Open examples/example.html. Try editing a setting, then save or discard it. The dashboard and list patterns are visual examples.
  3. Copy examples/example.html to a new file in the same folder.
  4. Remove sections you do not need, duplicate sections you do need, and replace the literal placeholder text.
  5. Refresh the browser. The examples link tokens.css by relative path, so copied files should stay inside the package folder.
  6. From the kit root, run python3 validate.py examples/my-screen.html when the screen looks finished. A browser renders a drifted screen at about 95% correct; the validator catches the rest.

You do not need to understand every component before starting. Build from the closest example, then use the reference when a choice is unclear.

Default workflow

  1. Pick the closest reference page.
  2. Compose with existing components before adding CSS. Copy their markup from the styleguide; do not reconstruct it from memory.
  3. Use .card for surfaces and .stack for vertical rhythm.
  4. When nothing fits, add a real component (see Extension protocol).
  5. Run validate.py on the file, then check it in a browser in light and dark.

How it works

The architecture in one sentence; the rules in this documentation follow from it.

Knobs set values → tokens name them → components consume them → screens compose them. Never let a layer reach around another.

The layers

LayerDefinitionModified when
Knobs--accent, --space-unit, --radius, widths, presetsSetting brand color, density, or shape
TokensSemantic roles (--color-text-primary, --gap-content)Not modified; they resolve from knobs
ComponentsBEM blocks consuming semantic tokens onlyWriting markup
ScreensCompositions of components, no page CSSBuilding screens

Configuration

:root {
  --accent: #7f54b3;        /* brand color; hover/soft derive */
  --space-unit: 3px;        /* compact rhythm (default 4px) */
  --radius: 0px;            /* square UI (default 4px) */
}

If no accent is set, the interface follows the administrator's wp-admin color scheme.

The block above configures the design pages. Inside wp-admin, the stylesheet is scoped to a plugin-specific wrapper class (see docs/wp-admin.md), and the same knobs are set on that wrapper instead — :root values do not reach the wrapper's scope there.

What the validator checks

The hard rules are nine, stated once in docs/contract.md §2 (R1–R9). Six consequences of them are mechanical; validate.py checks those, reading tokens.css at run time.

CheckCatches
undefined-tokenA var() that names no token in tokens.css. A var() with a fallback passes: that marks a deliberate input such as --fill.
unknown-classA class with no rule anywhere: invented BEM (.card__meta).
inline-styleAn inline declaration that is not a custom property.
raw-literal320px or #fff in a declaration value.
primitiveA primitive token (--gray-900) in markup.
page-cssA <style> block with anything but a :root knob block.

Two profiles. The guide pages (styleguide*.html, navigation-patterns.html) are scaffolding and run a relaxed set. Every other file is a screen and runs all six at zero tolerance; that is the profile your own files get.

The rules the validator cannot see are reviewed by eye: gap instead of margins (R2), one page header (R6), one primary action (R7), danger confirms through a modal (R8), labels are design and data is placeholder (R9).

python3 validate.py my-screen.html      # exit code 1 on failure; fits CI
python3 validate.py examples/*.html     # several files at once

Inside wp-admin

Use the preview pages to design. Scope the kit before rendering it inside WordPress.

  1. Wrap your plugin markup in a plugin-specific class, such as myplugin-admin.
  2. Remove the demo shell/admin chrome sections from your copy of the stylesheet.
  3. Prefix selectors so rules apply only inside the wrapper.
  4. Add the measured neutralizer before the scoped component rules.
  5. Move knob overrides from :root to the wrapper class.

The full procedure, including the neutralizer block, is in docs/wp-admin.md. It was validated against a real WordPress installation: 36 selector collisions before, zero after, in both directions.

Customize

Start with the small knob surface: accent, density, radius, widths, and mode. Change five numbers, get a different product.

:root {
  --accent: #7f54b3;       /* brand color */
  --accent-hover: #664491; /* hover color */
  --accent-soft: rgb(127 84 179 / 10%); /* tinted surface */
  --space-unit: 3px;   /* compact rhythm; default is 4px */
  --radius: 0px;       /* square UI; default is 4px */
}

The styleguide customizer produces the :root block interactively. Beyond the knobs, tokens.css is ordinary CSS. Keep the two-tier structure when editing: primitives feed semantic roles; components consume semantic roles. That keeps the styleguide truthful and dark mode working.

Tokens & knobs

Two tiers of custom properties and one branding knob. Components read the semantic tier only (R1); the tiers map 1:1 to design-tool variable collections.

Tier 1 — primitives

Raw values, never referenced by a component.

  • Color ramps: --gray-900…50, --white, --blue-700/600/400/300/50, --green-700/600/400/50, --yellow-600/50, --red-700/600/300/50.
  • Type: --font-size-11…23, --line-height-tight/base, --font-family, --font-mono.
  • Space: --space-unit (4px) and its multiples --space-4/8/12/16/24/40.
  • Radius: --radius-4/999. Size: --size-16/24/36/44/80/160/180.

Tier 1b — the accent knob

--accent, --accent-hover, --accent-soft, one set per mode. Every accent-colored role routes through them. See Color & accent.

Tier 2 — semantic roles

The only tokens components use. Light and dark are two modes of this tier.

  • Color: --color-{category}-{role} for text, bg, border, action, states, and focus.
  • Type: --text-xs/sm/md/lg, --heading-sm/md/lg/xl, --leading-heading/body.
  • Space: --space-xs/sm/md/lg/xl; rhythm: --gap-tight/label/content/section.
  • Radius: --radius (master), --radius-control, per-part --radius-button/card/input, --radius-full.
  • Size: --size-control/step/icon-tile/icon-tile-lg, --width-input-narrow/sidebar/setting-label; surface widths --width-*.

The same structure holds in a design tool, should you build one yourself: primitives as one collection with a single mode, semantic roles as one collection with Light and Dark modes, the accent trio as a rebindable variable set. Names are identical to the CSS custom properties.

Color & accent

One input, the accent, and a stable vocabulary of roles that consume it.

Resolution chain

An explicit brand override → the administrator's wp-admin color scheme, read from WP core's own --wp-admin-theme-color → the native admin blue. An unbranded plugin sets nothing and matches the user's scheme automatically, Ectoplasm included. The data-admin-scheme presets replicate the eight core schemes for static previews.

Why three values

Hover and soft cannot be derived from one color in CSS without color-mix(), and explicit knobs are what design-tool variables mirror 1:1. Brand = set the three: hover is the brand at HSL lightness −10, soft is a 10% alpha tint. The setup skill computes both from one hex.

--accent versus --color-action-*

--accent* is the input: where the color comes from. --color-action-primary, --color-text-link, --color-focus and their siblings are the consumption vocabulary: what the color is used for. Today the roles all alias the accent; the separation is load-bearing. You can override one role without touching a component ("brand the buttons, keep links blue" = override --color-text-link only), and the sourcing chain can change without a component edit.

Role categories

  • text: primary, secondary, inverse, inverse-muted, on-accent, link, link-hover
  • bg: canvas, surface, subtle, inverse · border: default, strong
  • action: primary, primary-hover, soft · focus
  • states: success, success-text, success-soft, warning, warning-soft, danger, danger-hover, danger-soft

--color-action-soft is for tinted fills only (icon tiles, soft surfaces), never for text. Promotion uses the soft action color, never a state color.

Contrast

About 29 real text and UI pairs per mode are audited at the default accent: text at AA 4.5:1, UI boundaries at 3:1, translucent softs composited over their real backgrounds. Dark mode passes clean. One pinned wp-parity exception remains: WP's red on the gray-50 surface at 4.40. Muted scheme accents such as Coffee produce greyish tints; adequate for chrome matching, not for brand expression.

Typography

The wp-admin system stack at wp-admin sizes, measured on WP 7.0, in eight roles.

Body font: the system stack (-apple-system, system-ui, Segoe UI, Roboto, …). Mono (--font-mono) for keys, shortcodes and code. Two leading roles: --leading-heading (tight) and --leading-body (base).

RoleSizeUsed for
--text-xs11pxtable column labels

  • The page title is the largest text on any screen; the plugin brand is --heading-md and never outweighs it.
  • Navigation labels (tabs, subnav, views, menu) are sentence case. List-table column headers keep the uppercase idiom; it is a separate register.
  • Type does not scale with density. Density tightens breathing room, not legibility.

Spacing, density & shape

One unit, linear multiples, four rhythm roles. Vertical space is flex + gap (R2).

The engine

Every spacing primitive is a multiple of --space-unit: ×1 ×2 ×3 ×4 ×6 ×10 gives 4 / 8 / 12 / 16 / 24 / 40. The roles alias them: --space-xs 4, -sm 8, -md 16, -lg 24, -xl 40. Multiples are linear, not a geometric ratio: a ratio produces off-grid fractions and cannot reproduce the 4px grid wp-admin sits on.

Rhythm roles

RoleDefaultOwns
--gap-tight8stacked controls, action clusters
--gap-label12a field label to its control(s)
--gap-content16blocks inside a card, drawer, or popup
--gap-section24page level: header, notices, cards

Containers own their rhythm through these roles. The .stack utility is the generic stacking frame: default gap is --gap-content; .stack--tight and .stack--loose use the tight and section roles. A gap that "does not work" is usually a missing .stack on the intermediate element, not a missing margin.

Density

data-density="compact" sets the unit to 3px (−25%); "relaxed" to 5px (+25%). Steps stay integers at all three presets. Type sizes and control hit areas (32px inputs, 16px checkboxes) do not scale. Breakpoints are constants (700px: settings rows stack; 960px: columns stack) because media queries cannot read custom properties.

Shape

Two radius tiers in the classic wp-admin register: containers a touch rounder (--radius, 4px: cards, panels, notices), controls crisp (--radius-control, half the master: buttons, inputs, checkbox, chips). One dial governs both, so --radius: 0 squares the whole interface; --radius-button, --radius-card and --radius-input re-round one part. Pills (badges, toggle, tags, stepper markers) use --radius-full and do not follow the master: they are a shape, not a roundness level.

Dark mode

data-theme="dark" swaps the semantic color tier (R5). Nothing else changes.

  • Set the attribute on <html> in the design pages; inside wp-admin, on the plugin wrapper (the scoping pass rewrites [data-theme] blocks to the wrapper).
  • Type, space, radius and size are mode-independent. No component carries dark-specific rules.
  • The accent brightens to the blue-300 grade with dark on-accent text; danger and success step up to text-grade primitives. Contrast is audited in both modes.
  • Three icons are CSS background images and cannot inherit currentColor: the select chevron, the checkbox check, the search icon. Their colors are pinned in utf8 SVG data URIs, with dark overrides for the chevron and the search icon. This is the only place a color bypasses the token cascade.
  • The wp-admin chrome (.shell, .admin-menu, .admin-bar) is fixed dark in both modes, as in WordPress.
  • A live switch: the .plugin__theme-toggle icon button, wired by [data-theme-toggle] in bios.js.

Icons

Tabler only (R4), delivered as an inline SVG sprite per page. Zero external requests, native currentColor.

<svg class="icon" aria-hidden="true"><use href="#i-settings"/></svg>
  • Each page carries a <svg data-bios-sprite> block with one <symbol id="i-{name}"> per icon it uses. The name in code is the Tabler name.
  • Sizes: .icon 18px, .icon--sm 14px, .icon--lg 22px. The spinner mirrors the same three sizes.
  • Icons are always aria-hidden="true"; the adjacent label carries the meaning. Icon-only controls get an aria-label.
  • To add an icon: take the file from icons/ (or the @tabler/icons npm package, verbatim) and add its paths as a <symbol> to the page sprite, or inline the SVG with class="icon". Never hand-author icon artwork; other sets tend to carry hardcoded fills that ignore state colors.
  • The three CSS background-image icons (select chevron, checkbox check, search) are the only icons outside the sprite.
  • The wp-admin chrome uses WP's own dashicons (icons/wp-*.svg, GPL); never in kit components. Licenses: THIRD-PARTY-LICENSES.md.

Reading a spec block

Every block has the same fields: the class names it covers, a purpose line, the anatomy (elements and their roles), modifiers, rules, accessibility, and the live demo with its markup. Copy the markup exactly; reconstructing a component's class structure from memory is where invented classes come from, and validate.py will flag them.

components.json

One entry per spec block: id, category, classes, the BEM blocks covered, purpose, the spec's API rows, variants, the design-tool mapping, and a canonical snippet. A tokens block lists the primitives by name (to recognize, not to use), the accent knob, and every semantic role with its light and dark value. Generated from the styleguide, so it never disagrees with it.

Full prose inventory by group, with the rules that belong to each block: docs/contract.md §5.

Reference screens

Six reference patterns in five pages, plus two guides. Start every new screen from a copy of one of them, never from a blank file.

  • example.html — the working reference. Dashboard (status card, getting-started checklist, stats), settings (single flush card with section titles, settings rows, save-bar) and list (views row, list-table with bulk actions, filters, pagination) on one screen.
  • shell-fullwidth.html — .plugin__body--full: no max-width, for wide tables.
  • shell-sidebar.html — sidebar-driven navigation, .columns main + aside of widget cards, a drill-in card with breadcrumb and .tabs--card.
  • shell-onboarding.html — no plugin chrome, a centered 560px panel with a stepper. Wizards carry no other navigation.
  • ai-components.html — the AI set in context: chat panel, inline suggestion beside a field, generate triggers, usage and consent.
  • navigation-patterns.html — the depth ladder and worked navigation patterns (guide page).
  • styleguide.html and the six group pages — foundations, customizer, and every component spec (guide pages).

The wp-admin chrome on these pages (admin bar, admin menu) is context, not design surface. Keep it complete; rename only the plugin's own menu item and submenu.

Navigation ladder

One primary navigation per screen, at most one titled secondary level, and depth by composing screens rather than stacking bars. The rules were validated against IA literature and four mature design systems; the reasoning is in docs/agent-heuristics.md §2b.

LevelFormNote
1 · PrimaryThe sidebar submenu, or, for a single-menu-item plugin, a chrome .tabs strip under the topbarOne or the other is the plugin's main switch between screens. Never both.
2 · Secondary (optional, max one).subnav--links · .tabs--boxed bare on the canvas · chrome .tabs under the page header · a titled .card--flush + .tabs--cardSection navigation within the current page. Always directly under a titled parent. Pick one by visual weight.
Filtering.views (pipes + counts) above a list-tableSame collection, filtered subsets. Not a level; coexists with either.
  • The labeled-parent test. Is there a title element directly between this strip and the level above it? Yes: legal nesting. No: the strip is misplaced; push a level to the sidebar submenu, move it into a drill-in card, or split the screen. A third row is never legal.
  • One row. A tab strip fits one row without wrapping. When items would wrap, restructure; never add a "More" tab as the default fix.
  • Breadcrumbs mark journey, not structure. A screen reached by drill-in (a list row, a link) carries a breadcrumb and a back link that preserves the list's filter and page. A screen selected from a visible parent strip does not.
  • Register. Single-purpose configuration registers under Settings (or Tools); a new top-level admin-menu item is justified only for a genuinely multi-screen product.

Worked frames for each pattern: examples/navigation-patterns.html.

Plan → confirm → build

Agent support starts after the human has a plugin goal, not after they read the whole manual.

Open the package folder in an agentic editor and describe the plugin. The folder carries the agent context (CLAUDE.md / AGENTS.md) and the bios-setup skill at .claude/skills/bios-setup/SKILL.md, which sequences the conversation in three beats. Claude Code loads the skill automatically; other agents can follow it as a procedure.

  1. Plan out loud. The agent proposes a screen list, each screen mapped to a reference pattern, the navigation model, and the component list per screen, and states its assumptions for the setup answers instead of interrogating.
  2. Confirm. You approve the screen list and navigation, and any gap the kit does not cover (compose, extend, or out of scope). A sitemap is cheap to change; five built screens are not.
  3. Build screen by screen. One HTML file per screen, copied from its reference page. Labels come from your plugin's domain; data stays placeholder. Each screen is validated and checked in light and dark before the next.

Extension protocol

Custom UI is expected. BIOS is a baseline, not a ceiling; the custom piece should be indistinguishable from a kit component in code review.

  1. Compose first. Most "custom" needs are existing components in a new arrangement; cards, stacks and panels cover a lot.
  2. Extend properly. Build the new piece as a real component in tokens.css: a BEM block in its own section, semantic tokens and knobs only, gap-based stacking, a focus-visible state. Dark mode then comes for free.
  3. Never the shortcuts: inline styles, one-off CSS with raw values, primitives in markup, margins. That is the rot vector, not customization itself. R1–R3 apply to the new component as to the kit's own; validate.py enforces them.
  4. If a custom piece will be reused across screens, treat it as part of your product's component layer; it may also belong upstream in BIOS.
